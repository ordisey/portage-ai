Part 2

Singapore Telco Mobile App — SIMBA

Top 3 features, with rationale and prioritization. Kept short on purpose — the brief itself asks for a quick read on product thinking, not a second prototype.

SIMBA's proposed acquisition of M1 didn't go through — IMDA suspended its review in May 2026 over a spectrum-licensing investigation, and the deal was terminated. That leaves SIMBA where it's actually been most effective: a lean, digital-first challenger competing on price, transparency, and simplicity rather than network scale. That's the lens I used below.
01

Usage & billing you can trust at a glance

P0 · first

Real-time data / talktime / rollover balance, proactive low-balance and bill-change alerts, and a plain-language breakdown of every charge.

Why — SIMBA's entire pitch (no contract, no hidden fees, free 6-cycle rollover) is a trust claim. If the app doesn't make that promise instantly legible — and current My SIMBA reviews mention it can be slow to load and has crashed — the brand's whole differentiator disappears at the exact moment it matters: the moment someone checks if they're about to pay more.

Priority — the cheapest, most foundational move I can make. It's data SIMBA already has, just not legible yet, and it protects revenue through retention.

02

Instant self-serve for everything

P0 / P1 · parallel

One-tap eSIM activation and porting, in-app plan switching, and simple multi-line / family management — no store visit, no call.

Why — SIMBA doesn't have a retail footprint like Singtel or StarHub — the app is the storefront. Every point of friction either sends a customer to a competitor with a shop, or into a support queue that costs more per interaction than a lean challenger can afford. It's also the biggest growth lever they have: "switch to SIMBA, it took three minutes."

Priority — build alongside #1. I'd rank it second only because the scope — eSIM, porting integrations — is bigger.

03

A support assistant that actually resolves things

P2 · sequenced last

An in-app assistant that answers billing / roaming / outage questions instantly, walks a customer through eSIM or roaming setup, and escalates to a human only when it genuinely needs one.

Why — this is where SIMBA's cost structure and its customers' expectations meet. Routine questions — why did my bill change, how do I turn on roaming, is there an outage — are the highest-volume, lowest-value tickets a support team gets, and every one a live agent handles is scale-player money a challenger doesn't have. Done well, it also builds trust instead of eroding it: fast, clear answers instead of hold-the-line frustration.

Priority — last, on purpose. It only works once the usage/billing data from #1 is clean and the self-serve actions from #2 actually exist for it to use. Build it first and you'd ship an assistant that can explain a problem but can't fix it.

How I prioritized — three questions, in this order: does it protect the trust the brand is already promising, does it cut cost-to-serve or friction in the one channel a no-storefront challenger actually has, and what depends on what. Feature 3 is arguably the most interesting of the three strategically — but putting it last, behind the data and actions it needs to be useful, is itself the call this exercise is testing.

Scope

Why I built a freight operations copilot

The brief fixes the domain — an AI-first agentic logistics app. "Logistics" is broad enough to hide the real question, so I narrowed this POC to one sharp vertical instead of a generic tracker.

The brief

  • Identify the top 3 agentic functions
  • Provide a scoping pack
  • Build a basic, interactive prototype
  • Include a GitHub repository

The read

I narrowed this to a freight/parcel operations copilot — the sharpest small system to prove exactly what this role is testing for:

2

Product roadmap

Now, Next, Later — paced by evidence, not a calendar

① NOW · this POC

Prove the agents reason correctly on realistic scenarios, with guardrails, before touching a live system.

  • Ship the interactive prototype
  • Define tool contracts for all 3 agents
  • ~20–30 golden eval scenarios / agent

Exit — eval results + reviewer feedback justify a real pilot.

② NEXT · one design partner

Replace mocked tools with real integrations on one contained lane — human approves every action.

  • Wire real TMS / carrier / EDI APIs
  • Tune guardrail thresholds on real decisions
  • Track cost + latency, not just accuracy

Exit — agent recs match a human ops lead ≥90% of the time.

③ LATER · expand autonomy

Turn on auto-execution for guardrail-cleared paths; widen from one lane to the full book of business.

  • Auto-execute only what Next proved safe
  • Per-account guardrail tuning
  • Standing eval regression suite

Exit — paced per-surface by trust earned in Next.

3

The top 3 agentic functions

One shipment, three agents, one human approval queue

L · Lane Agent

Books shipments: parses the request, ranks compliant carriers against live rates and routing rules, books or escalates.

  • Tool use: rates & booking APIs
  • Guardrail: rate-variance cap
  • HITL: escalates above threshold
W · Watch Agent

Monitors in-transit shipments: detects exceptions, diagnoses cause, proposes ranked remediation options.

  • Tool use: tracking & EDI feeds
  • Guardrail: cost-impact cap
  • HITL: never auto-cancels/claims
D · Doc & Comms Agent

Reconciles paperwork against the shipment record and drafts plain-language customer updates.

  • Tool use: document extraction
  • Guardrail: materiality threshold
  • HITL: approves before send

System architecture

One pattern, shared memory, one approval queue

Triggers

  • New shipment request
  • Tracking / EDI event
  • Document received

Orchestrator

plan → act → observe → escalate-or-continue

  • Lane Agent
  • Watch Agent
  • Doc & Comms Agent

Tools & shared state

  • Carrier rate & booking API
  • Tracking / EDI feed
  • Customs & policy RAG store
  • Shipment memory · approval queue · audit log

Nothing here is a capability I invented for the demo — every mocked tool call maps to a named real integration point, so getting from this POC to a pilot is a list of integrations, not a redesign.

6

Trust, by design

Guardrails ops can see, and an eval pipeline that proves it works

Guardrails

  • Lane Agent — rate variance 15%
  • Watch Agent — cost cap $250
  • Doc Agent — materiality 1.5%

Customs / regulatory changes always require human sign-off, regardless of threshold.

How I'd evaluate it

  • Golden scenarios, ~20–30 per agent
  • Rule-based checks first
  • LLM-as-judge for the rest
  • Production shadow metrics from real approve/reject calls
